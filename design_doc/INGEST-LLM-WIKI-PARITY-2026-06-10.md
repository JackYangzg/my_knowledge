## Problem Statement

当前 Android 项目声称多处 ingest 逻辑与 `llm_wiki` 1:1 对齐，但代码级核对表明，两者只在“两个 LLM 阶段、FILE/REVIEW 输出、部分上下文预算、frontmatter 字段并集”这些外形上相似。分析结果格式、提示词语义、数据源、长文档汇总、页面合并、实体/概念去重、缓存命中条件和写入模型均存在会改变最终知识库内容的差异。

本设计以以下版本为固定基线：

- `llm_wiki`: `/Users/yangzhiguo/project/llm_wiki`, `main@b86d81b0002afcee981169658c7602b8ec5f8905`, 2026-05-29
- `my_knowledge`: `feature/ingest-budget-align@6954fff8b8007b8965a8844a4351c13b0edb7e31`，包含 2026-06-10 当前工作区未提交改动

“完全一样”的定义不是类名或注释相似，而是同一源文档、同一模型响应、同一既有 Wiki 状态下，两边产生等价的：

1. LLM system/user messages
2. 长文档 chunk 输入和中间汇总
3. FILE/REVIEW 解析结果
4. 页面路径、frontmatter 和正文
5. 既有页面合并结果
6. 实体/概念重复检测和用户确认后的合并结果
7. cache hit/miss 决策

## Audit Result

结论：**当前实现没有与 llm_wiki 完全一致，且不能通过小修补达到完全一致。**

### P0-1: Stage 1 契约完全不同

`llm_wiki/src/lib/ingest.ts:1306` 的 `buildAnalysisPrompt` 要求 Markdown 分析，包含 Key Entities、Key Concepts、Main Arguments、Connections、Contradictions、Recommendations。

Android 的 `AiPromptTemplates.analysisPrompt` 要求严格 JSON，并额外规定：

- entities 1-10、concepts 1-8
- entityType / conceptCategory
- relations / claims / gaps / archiveRecommendation
- 至少 1 个 entity 和 concept，与后文“短源允许空数组”互相矛盾

这不是同一提示词的跨语言实现。它会改变模型思考任务、输出长度、实体选择和 generation 输入。

### P0-2: Stage 2 使用的 analysis 数据不同

`llm_wiki` 将 Stage 1 的完整 Markdown 分析原样放入 generation user message。

Android 只取 `analysis.summary`，再自行拼接 `entitiesJson`、`conceptsJson`、`relationsJson` 的压缩 Markdown。它还要求这些结构化节点成为“source of truth”。

因此即使模型相同，Stage 2 看到的事实、证据、矛盾、建议和页面优先级也不同。

### P0-3: Generation prompt 增加了 llm_wiki 不存在的页面类型

Android 强制或鼓励生成：

- `wiki/papers/`
- `wiki/methods/`
- OmegaWiki 风格 paper sections
- paper/method 专用 frontmatter

基线 `llm_wiki` 的 `GENERATION_WIKI_TYPES` 是：

`source, entity, concept, comparison, query, synthesis, thesis, methodology, finding`

Android 的 known types 和 WIKI_SCHEMA 则包含 `paper, method, overview`，并遗漏 `thesis, methodology, finding`。路由和最终页面集合不一致。

### P0-4: 既有页面合并算法不同

`llm_wiki` 对除 index/overview/log 外的既有内容页执行：

1. sources/tags/related 确定性并集
2. 正文不同时调用 LLM merge
3. 拒绝无 frontmatter 的输出
4. 拒绝正文短于两侧最大正文 70% 的输出
5. 失败时保留 incoming，并备份 existing
6. 锁定 type/title/created，updated 写当天

Android 热路径明确不调用 `requestAiMerge`，而是：

- entity/concept: 按章节确定性 union/追加
- index/overview: 按章节 bullet union
- 其他页面: `WikiPageCompiler.merge`，正文后附 `## 合并自旧页面`

两边在信息去重、章节重组、失败回退和历史正文保存方式上均不等价。

### P0-5: index/overview 写入语义相反

`llm_wiki` 对 `wiki/index.md` 和 `wiki/overview.md` 直接整体覆盖，认为它们是全局快照，不应做来源页面合并。

Android 对两者做历史章节并集。这会保留 llm_wiki 本会删除的陈旧条目，也可能让 overview 永远膨胀。

### P0-6: ingest 内实体/概念身份归并不是 llm_wiki 行为

Android 当前在 ingest 热路径加入：

- NFKC + Unicode 空白归一化
- case-insensitive dedup
- title 精确匹配
- slug 模糊匹配既有行
- re-analysis 时 old/new entities、concepts 按 name 并集

`llm_wiki` ingest 只按模型给出的文件 path 定位页面。跨名称别名合并由独立 dedup 流程处理：

1. LLM 扫描全部 entity/concept
2. 输出候选组
3. 用户确认 canonical slug
4. LLM 合并正文
5. 重写全 Wiki wikilink/related
6. 备份所有受影响页面
7. 删除被合并页面

Android 的自动模糊合并既可能误并，也没有实现用户确认、全局引用重写和可回滚备份。

### P0-7: 长文档分析算法不同

`llm_wiki` 每个 chunk 输出两个 Markdown section：

- Chunk Analysis
- Updated Global Digest

完成后将 digest + per-chunk analyses 作为 Stage 1 分析和 Stage 2 source context。

Android 每个 chunk 输出完整 ANALYSIS_SCHEMA JSON，然后程序化 union entities/concepts/relations/claims/gaps，并用最新 chunk 的 summary 作为滚动 digest。

两者的跨 chunk 信息保留、名称稳定、冲突处理和 generation 上下文不同。

### P0-8: chunker 实现未证明一致

`llm_wiki` 在 `ingest.ts` 内按 Markdown heading、段落、句子拆块，并按前一块后缀生成 overlap。

Android 使用 `MarkdownSemanticChunker`。虽然参数公式相同，但当前没有共享 fixture 证明 chunk 文本、headingPath、overlapBefore、chunk count 完全一致。

### P0-9: source identity 与 source summary path 不一致

`llm_wiki` 使用 `raw/sources/` 下的相对路径作为 sourceIdentity；同名文件位于不同子目录时，通过编码路径 + FNV hash 生成不同 summary slug。

Android generation 使用 `source.title`，summary path 固定为去扩展名后的标题。不同目录中的同名文件可能映射到同一个逻辑 source 页面。

Android 长文 checkpoint identity 又使用 `${source.id}:${source.sha256}`，与 llm_wiki 的相对路径 identity 不一致。

### P0-10: cache 契约不同

`llm_wiki` cache key 是 sourceIdentity，命中条件为：

- 内容 SHA256 相同
- 上次记录的每个 filesWritten 仍存在

Android cache 通过数据库中相同 SHA256 的 sibling source 判断，并额外要求：

- sibling 已 generated
- analysis promptVersion 为当前版本
- 非 reprocess

Android 的策略可能跨路径复用同内容，也会因 promptVersion 主动失效；两者都合理，但不是同一行为。

### P1-1: 模型调用参数未形成 parity 契约

`llm_wiki` 明确设置：

- temperature 0.1
- reasoning off
- analysis max_tokens 4096
- generation max_tokens 按 context 档位

Android temperature 对齐，但通过不同 gateway、JSON schema 调用和重试包装执行。需要记录最终 provider request 才能证明 reasoning、max tokens、system/user 排序和 schema 尾注完全一致。

### P1-2: Android template fallback 改变页面集合

Android 始终执行 `wikiCompiler.compile`，再以 AI pages 优先、template pages 补缺。

`llm_wiki` 正常 AI ingest 不会用本地模板补齐 entity/concept 页面，只保证 source summary fallback。Android 因此可能生成模型没有要求生成的页面。

### P1-3: root KnowledgeItem 是 Android 特有产物

Android 在 generation 开始时写入原始 source root item，并把原文作为 `contentMarkdown`。这可以保留，但必须明确它是平台适配层，不属于 llm_wiki parity surface；否则“产物完全一样”无法成立。

## Premises

1. `llm_wiki@b86d81b` 是唯一行为基线；旧设计稿和 Android 注释不作为基线。
2. parity 层只负责纯 ingest 语义；Room、WorkManager、KnowledgeItem root row、通知和 Android 生命周期属于 adapter 层。
3. 为了真正一致，应移植 llm_wiki 的纯函数和状态机，而不是继续手工“解释性翻译”提示词。
4. Android 特有增强不能混入 parity 默认路径。需要保留时，必须放到显式 compatibility flag 后。
5. 没有跨仓 golden fixtures 和模型响应回放测试，就不能使用“1:1”或“完全一致”表述。

## Approaches Considered

### Approach A: 文本修补

只修改 Android prompt 文本和几个 merge 分支，使其更像 llm_wiki。

Effort: S
Risk: High

Pros:

- 改动文件少
- 可以快速消除最明显的 prompt 差异

Cons:

- 长文、cache、source identity、dedup、写入顺序仍不同
- 下次 llm_wiki 更新后会再次漂移
- 无法客观证明完全一致

### Approach B: 行为级 Kotlin 镜像

以 `llm_wiki` 的 ingest 纯函数为规范，在 Kotlin 中逐函数镜像，并建立同 fixture、同 response 的 golden parity tests。

Effort: L
Risk: Medium

Pros:

- 保留原生 Android/Room/WorkManager 架构
- 可通过测试证明每个纯函数和最终产物等价
- 能把 Android 特有生命周期逻辑隔离在 adapter 层

Cons:

- 需要删除或隔离当前若干“增强”
- TypeScript 与 Kotlin 双实现仍有长期同步成本

### Approach C: 共享 ingest 核心

把 llm_wiki ingest 核心抽成可版本化共享模块，通过 JS runtime、WASM 或独立本地服务供 Android 调用。

Effort: XL
Risk: High

Pros:

- 单一实现，长期最不容易漂移
- prompt、parser、merge、dedup、cache 可真正共享

Cons:

- Android 集成和发布复杂度高
- 文件系统、取消、流式输出、数据库适配成本大
- 当前目标下属于大规模架构迁移

## Recommended Approach

选择 **Approach B: 行为级 Kotlin 镜像**。

它是当前唯一能在不重写整个 Android 技术栈的前提下，满足“与指定 llm_wiki commit 完全一样”并给出自动证据的方案。

## Implementation Plan

### Phase 1: 固定上游规范

新增 `ingest-parity/upstream.json`：

```json
{
  "repo": "/Users/yangzhiguo/project/llm_wiki",
  "commit": "b86d81b0002afcee981169658c7602b8ec5f8905",
  "capturedAt": "2026-06-10"
}
```

把以下上游函数登记为 parity surface：

- `sourceIdentityForPath`
- `sourceSummarySlugFromIdentity`
- `computeIngestSourceBudget`
- `computeIngestGenerationMaxTokens`
- `splitSourceIntoSemanticChunks`
- `buildAnalysisPrompt`
- `buildGenerationPrompt`
- `parseFileBlocks`
- `sanitizeIngestedFileContent`
- `mergePageContent`
- `checkIngestCache`
- dedup detector / merge / reference rewrite

### Phase 2: Prompt 与 Stage 1/2 数据流对齐

修改：

- `data/ai/AiPromptTemplates.kt`
- `data/ingest/IngestOrchestrator.kt`

要求：

1. Stage 1 恢复为 llm_wiki Markdown analysis，不使用 ANALYSIS_SCHEMA JSON。
2. generation user message接收完整 Stage 1 analysis，禁止自定义 structured source-of-truth block。
3. generation prompt 的 types、schema routing、source summary exact path、页面清单逐行对齐。
4. `source.title` 不再充当 sourceIdentity；使用 `raw/sources` 相对路径等价字段。
5. Android 若仍需结构化 graph 数据，在 FILE 写入后从生成页面解析，或作为 parity ingest 完成后的独立派生步骤。

### Phase 3: 长文档路径对齐

要求：

1. Kotlin chunker 对同 fixture 产生与 TypeScript 完全相同的 chunks。
2. chunk prompt 改为两个 Markdown section。
3. checkpoint 字段、兼容性判断、hash 和 identity 对齐。
4. consolidated analysis 与 sourceContext 文本逐字符对齐。
5. checkpoint 仅在整条 ingest 成功后清理，失败和取消保留。

### Phase 4: 写入和页面合并对齐

要求：

1. log append。
2. index/overview overwrite。
3. 其他 content pages 使用 LLM merge。
4. 应用 70% body shrink guard。
5. merge 失败或输出非法时写 incoming + array union，并备份 existing。
6. 锁定 type/title/created，updated 使用 UTC date。
7. Android 当前 section-aware merge 移出 parity 路径。
8. template fallback 只保留 llm_wiki 同等的 source summary guarantee。

### Phase 5: dedup 对齐

要求：

1. ingest 不做 slug 模糊自动合并。
2. ingest 不跨 re-analysis 保留旧 entities/concepts inventory。
3. 新增独立 duplicate detection。
4. 用户选择 canonical page 后才执行 merge。
5. merge 后重写所有 Wiki 页面中的 wikilink 和 related。
6. 备份全部受影响页面，再删除非 canonical 页面。
7. 保存 not-duplicates whitelist，比较时忽略顺序和大小写。

### Phase 6: cache 对齐

要求：

1. key 改为 sourceIdentity。
2. value 保存 content hash、timestamp、filesWritten。
3. 命中前校验全部 written artifacts 仍存在。
4. promptVersion 失效策略若保留，放在非 parity 扩展 flag 后，默认关闭。
5. 同内容不同路径不能互相命中。

### Phase 7: Android adapter

以下行为保留在 parity 核心之外：

- Room row upsert
- source root KnowledgeItem
- WorkManager queue 和前台通知
- graph rebuild
- embedding
- Android 文件导入 URI/权限处理

adapter 只能消费 parity 核心输出，不得改变 prompt、FILE pages、merge 和 dedup 决策。

## Verification

### Golden fixture runner

从 `llm_wiki` 导出固定 fixtures：

- 空源、短源、中文源、英文源
- 同名文件位于不同目录
- 128K/256K/512K context
- 多 heading 长文
- CRLF、truncated FILE block、unsafe path
- 新页面、同正文不同 sources、正文冲突页面
- LLM merge 失败、无 frontmatter、正文缩短到 69%/70%
- entity/concept alias 候选和 cross-reference rewrite

每个 fixture 保存：

- system prompt
- user prompt
- chunks/checkpoint
- mocked LLM responses
- parsed FILE/REVIEW blocks
- final virtual filesystem manifest

Android 测试读取同一 fixture，断言：

1. prompt 字符串逐字符相同，仅允许显式登记的平台换行差异。
2. chunk 文本、顺序、overlap 相同。
3. 模型响应解析结果相同。
4. 最终路径集合、frontmatter、body 相同。
5. merge、backup、delete、reference rewrite 相同。
6. cache hit/miss 相同。

### Acceptance Criteria

- parity fixture 100% 通过
- Android 默认 ingest 不再包含未登记的增强语义
- 所有偏离上游的行为都有 feature flag 和独立测试
- CI 输出基线 commit，并在上游 commit 改变时强制重新生成/审核 fixtures
- 删除代码中未经测试支撑的“1:1 alignment”注释

## Open Questions

1. Android 是否接受 Stage 1 从 JSON 回退为 Markdown？这是完全一致的必要条件。
2. Android graph 的结构化 entities/relations 是从生成页解析，还是在 parity ingest 后再做一次独立 LLM 派生？
3. Android 当前的自动实体保留和 slug 模糊合并是否允许默认关闭，改为用户确认 dedup？
4. 基线是否固定为 `b86d81b`，还是要先把 `/Users/yangzhiguo/project/llm_wiki` 更新到另一个明确 commit？

## Success Criteria

对同一 fixture 和固定模型响应，Android 与 `llm_wiki@b86d81b` 的 parity core 输出无差异；任何 Android 特有行为只发生在 core 输出之后。

## Next Steps

1. 先建立跨仓 golden fixtures，不改业务逻辑。
2. 用 fixture 测试逐项暴露当前差异。
3. 按 Prompt/Data Flow → Long Source → Merge → Dedup → Cache 顺序收敛。
4. 每收敛一层就删除对应的自定义分支，避免新旧语义同时存在。

## What I noticed

- 现有代码里多处写着“1:1 alignment”，但真实实现常在下一段加入 Android 自定义语义。注释现在会误导维护者。
- 当前分支正在加入 entity 名称规范化、slug 模糊合并和跨 analysis 保留。这些是在修用户可见的数据丢失，但方向与 llm_wiki 的“候选检测 + 用户确认合并”不同。
- `ContextBudgetCalculator` 是少数已经接近逐公式移植的模块，适合成为 parity 测试的第一个样板。
