## 2. DRY 违规

### CQ-1：`AiGateway` 4 处重复 try/catch + 错误分类模板（P0）

**位置**：`AiGateway.kt` 4 个独立方法（`callApi`, `completeStreamObserved`, `streamJsonObserved`, `analyzeImage`）

**重复模式**（每处约 50 行）：
```kotlin
try {
    // ... HTTP request
} catch (e: java.net.UnknownHostException) {
    throw AiException("[$TAG][DNS 失败]...", e)
} catch (e: java.net.SocketTimeoutException) {
    throw AiException("[$TAG][超时]...", e)
} catch (e: javax.net.ssl.SSLException) {
    throw AiException("[$TAG][SSL 错误]...", e)
} catch (e: java.io.IOException) {
    throw AiException("[$TAG][连接失败]...", e)
} catch (e: AiException) {
    throw e
} catch (e: Throwable) {
    throw AiException("[$TAG][未知错误]...", e)
}
```

**修复方向**：
```kotlin
// 抽 toAiException(scope: String, e: Throwable): AiException
private fun toAiException(scope: String, e: Throwable): AiException = when (e) {
    is AiException -> e
    is UnknownHostException -> AiException("[$scope][DNS 失败]...", e)
    is SocketTimeoutException -> AiException("[$scope][超时]...", e)
    is SSLException -> AiException("[$scope][SSL 错误]...", e)
    is IOException -> AiException("[$scope][连接失败]...", e)
    else -> AiException("[$scope][未知错误]...", e)
}

// 调用方: HttpRequest::execute.catch { throw toAiException("streamJson", it) }
```

**影响**：减重 ~200 行；统一错误消息格式；以后加新 scope（"image" / "embedding"）只改 1 处。

### CQ-3：`LlmInspirationThreadWorker` 手写 JSON 拼装（P1）

**位置**：`LlmInspirationThreadWorker.kt:283-289, 338-340, 350-352, 261-269`

**问题**：
```kotlin
private fun jsonArray(values: List<String>): String =
    if (values.isEmpty()) "[]"
    else values.joinToString(",", "[", "]") { "\"${escape(it)}\"" }

private fun escape(s: String): String =
    s.replace("\\", "\\\\").replace("\"", "\\\"").replace("\n", " ")
```

4 处自实现 JSON encoder（`jsonArray`, `escape`, `toJson`, `serializeDiff`），且 `escape` 在 3 个不同 data class 重复定义。

**风险**：
- 标题含 `"`、反斜杠、`\n` 时可能损坏
- 没有 Unicode 转义
- `replace("\n", " ")` 会把换行压成空格——可读性下降但合法
- 未来加新字段（`confidence: 0.5`）需要手写 → 容易出错

**修复方向**：
- 引入 `kotlinx.serialization`（已加入 kotlin plugin） + `@Serializable` data class
- 或退一步用 `JSONArray` / `JSONObject`（已 import）构造而不是手写字符串

**影响**：减重 ~40 行；消除 escape 不一致风险；与 `ParseAiAnalysisJsonTest` 已有模式一致。

### CQ-5：`AppDatabase` Migrations 顺序异常（P2）

**位置**：`AppDatabase.kt:77, 252-281`

注意：`MIGRATION_8_9` 在 `MIGRATION_7_8` **之后**声明，但 `MIGRATION_4_5` 在最前。然而 `addMigrations(...)` 调用是顺序的——但每个 Migration 独立 `object`，顺序不影响。

但 `MIGRATION_5_6` 在 `MIGRATION_7_8` 之后声明（`MIGRATION_5_6` 在文件第 261 行），而 `addMigrations(MIGRATION_4_5, MIGRATION_5_6, MIGRATION_6_7, MIGRATION_7_8, MIGRATION_8_9)` 引用它们。这是 Kotlin 编译期决定的，可读性差。

**修复方向**：按版本号顺序声明 Migration。

## 3. 错误处理

### CQ-6：`moveItemToBase` try/catch 仅用于日志（P1）

**位置**：`KnowledgeRepositoryImpl.kt:352`（估计行号）

```kotlin
try {
    db.runInTransaction { ... }
} catch (e: Exception) {
    Log.e(TAG, "moveItemToBase failed: $e", e)
    throw e  // ← 关键：重新抛出
}
```

**评价**：
- 优点：错误信息带上了"moveItemToBase failed"上下文
- 缺点：try/catch 没做任何错误恢复就 throw——这是"装饰性"异常处理

**修复方向**：
- 方案 A：去掉 try/catch，让 `runInTransaction` 自身抛
- 方案 B：catch 后包装为 `AppError.Database("moveItemToBase", e)` 后抛

---

### CQ-7：`RebuildDebouncer` 静默吞掉非 cancellation 异常（P1）

**位置**：`RebuildDebouncer.kt:194-208`

```kotlin
.collectLatest {
    try {
        action()
    } catch (ce: CancellationException) {
        throw ce
    } catch (t: Throwable) {
        Log.e("RebuildDebouncer", "Rebuild action failed for kb=$kbKey kind=$kind ...", t)
        // ⚠ swallow
    }
}
```

**问题**：
- 用户无感知失败
- 某 KB 持续失败时，UI 永远显示旧图
- 没有重试退避策略

**修复方向**：
- 至少写一个 `ReviewItem` 实体标记"自动重建失败，用户请手动重试"
- 或加一个"健康监控"接口，UI 可查询"最近一次成功时间"

## 4. 不可变性

### CQ-8：Room 实体使用了可变结构（部分）（P2）

**位置**：多数 `*Entity` 是 `data class`（不可变），但 JSON 列内容仍是 string。`KnowledgeThreadEntity.mainlineJson` 是 String，`KnowledgeRepositoryImpl` 更新时要 read-modify-write：

```kotlin
val existing = repository.getThreadByKb(kbId)
val updated = existing.copy(
    mainlineJson = jsonArray(newMainline),
    ...
)
repository.saveThread(updated)
```

这本身没问题（`copy` 是不可变），但 **如果 LLM 解析过程中同时有写入**就有竞态。

**修复方向**：
- 短期：保持现状
- 长期：所有写 `*Entity` 路径走 Repository 的事务方法，强制全字段替换

## 5. 可测性

### CQ-9：`AiGateway` 用 `HttpURLConnection` 而非 OkHttp 客户端（P2）

**位置**：`AiGateway.kt` 全文

**问题**：
- 难以 mock HTTP（必须用 `MockWebServer` + `LocalServer` 反射）
- 没有拦截器/重试中间件
- `connect()` / `disconnect()` 配对易漏

**修复方向**：保持现状（项目约束用 `HttpURLConnection`），但把 HTTP 边界抽到 `HttpExecutor` 接口便于测试。`AiGatewayStreamTest` 已经验证这条路径可行。

### CQ-10：`IngestOrchestrator` 是 `class` 而非 `interface`（P0）

**位置**：`IngestOrchestrator.kt`

**问题**：
- 2793 行实体类，没有 interface
- `IngestRuntime` 直接 `new IngestOrchestrator(...)`——无法替换为 fake

```kotlin
interface IngestOrchestrator {

class IngestOrchestratorImpl(

    private val rebuildDebouncer: RebuildDebouncer,
    private val longSourceCheckpointStore: LongSourceCheckpointStore,

```

这是 ARCH-3 拆分的前置条件。
