## 2. P0 测试缺口

### TC-1：`IngestOrchestrator.runUntilIdle` 4 轨并行无测试（P0）

**风险**：
- 4 轨并发下，假设某次重构把 `withContext(IO)` 改回 `withContext(Default)`，所有不变量破
- `AtomicInteger` 误换为 `Int` → 计数竞争
- 锁释放顺序反了 → 死锁

**推荐测试**（用 `runTest` + `TestScope`）：
```kotlin
@Test
fun `4 轨并行执行, 跨 KB 完全并行`() = runTest {
    val orchestrator = IngestOrchestratorImpl(fakeDb, ...)
    val tasks = listOf(
        makeTask(kbId = "kb1", type = "parse"),
        makeTask(kbId = "kb2", type = "parse"),
        makeTask(kbId = "kb3", type = "parse"),
        makeTask(kbId = "kb4", type = "parse"),
    )
    fakeDb.queuedTasks = tasks
    val maxParallel = AtomicInteger(0)
    fakeDb.onTaskStart = { maxParallel.updateAndGet { maxOf(it, currentParallel.incrementAndGet()) } }
    orchestrator.runUntilIdle(maxTasks = 8, parallelism = 4)
    assertEquals(4, maxParallel.get())  // 4 个同时跑
}

@Test
fun `同 KB 写锁串行, 跨 KB 并行`() = runTest {
    // ...
}

@Test
fun `cooperative cancel 让流式 LLM 立即退出`() = runTest {
    val cancelJob = launch { orchestrator.runUntilIdle() }
    advanceTimeBy(100)
    cancelJob.cancel()
    cancelJob.join()
    assertTrue(cancelJob.isCancelled)
}
```

## 3. 推荐测试策略

### 3.1 测试金字塔目标

```
        ╱  ╲
       ╱ E2E ╲          ← 0%  (无可用框架，且移动端价值有限)
      ╱───────╲
     ╱ 集成测试  ╲       ← 30%  (AppDatabase 迁移 + KnowledgeRepository 端到端)
    ╱─────────────╲
   ╱   单元测试     ╲    ← 70%  (各组件独立测试)
  ╱─────────────────╲
```

### 3.2 测试基础设施缺口

| 缺口 | 影响 | 推荐 |
| --- | --- | --- |
| 没有 `TestDispatcher` 的统一配置 | 测试 flaky | 抽 `TestDispatcherRule` |
| 没有 `FakeAppDatabase`/`InMemoryDatabase` | 集成测试难写 | 已有 `inMemoryDatabaseBuilder` 但未在测试中使用 |
| 没有 Mock LLM 的统一 fake | LLM 路径测试难 | 写 `FakeAiGateway` 实现 `AiProvider` 接口 |
| 没有 time provider | "5 分钟超时"类逻辑测不了 | 抽 `Clock` 接口（用 `Clock.System` 默认） |

### 3.3 推荐的 5 个 P0 测试用例

| # | 名称 | 覆盖 | 工作量 |
| --- | --- | --- | --- |
| 1 | `runUntilIdle 4 轨并发 + 同 KB 串行` | TC-1 | 1 天 |
| 2 | `rebuildGraphForBase dedup + blacklist` | TC-2 | 1 天 |
| 3 | `AiGateway 错误分类` | TC-3 | 0.5 天 |
| 4 | `AiGateway 完整流式 JSON happy path` | 部分已覆盖 | 0.5 天 |
| 5 | `IngestRuntime start/cancel/rerun` | TC-4 | 0.5 天 |

**总计 3.5 天**，即可把关键路径测试覆盖从 20% 提升到约 60%。

## 4. 现有测试质量评估

### 4.1 优秀测试（值得保留并扩展）

- **`RebuildDebouncerTest`**：覆盖 4 种去抖窗口、per-KB 隔离、失败隔离、shutdownForTests——这是教科书级别的协程测试
- **`IngestQueuePolicyTest`**：极简但 100% 覆盖
- **`ParseAiAnalysisJsonTest`**：含空/异常/多语言 case

### 4.2 弱测试（需重写）

- **`KnowledgeEntityKindTest`**：trivial enum 测，删除或合并
- **`InspirationThreadPromptTest`**：snapshot 风险（prompt 字符串微调就 fail）——应改为"含有关键字"或"结构化字段"测试

### 4.3 缺失的测试类型

| 类型 | 现状 | 需求 |
| --- | --- | --- |
| 集成测试（Repository + DB） | 0 个 | 至少 3 个核心方法 |
| 端到端测试（Worker 链路） | 0 个 | IngestWorker / LlmInspirationThreadWorker |
| 性能测试 | 0 个 | 4 轨并发的吞吐基准 |
| 故障注入测试 | 0 个 | DB 失败 / LLM 失败 / OOM |
| 并发测试 | 0 个 | 4 轨互不饿死 |
| 迁移测试 | 1 个（v4→v9 路径）| OK，但缺"任意 v→v9"路径 |
