# 执行摘要

> 评审对象：`my_knowledge` Android 应用的整个数据/AI/持久化层（`com.my.knowledge.data.*` + `com.my.knowledge.worker.*`）
> 评审方式：源码逐文件精读（约 6000+ 行核心代码）+ 测试覆盖盘点 + 业务流程追踪
> 评审日期：2026-06-04

## TL;DR

工程实现了一个相对完整的"本地优先 + LLM 增强"知识库：4 阶段摄入管线（parse → analysis → generation → embedding）、4 轨并行调度器、3 道去抖（graph/sweep/thread）、3 道可恢复检查点（cache hit、长源 checkpoint、cooperative cancel）。架构方向已经稳定，**P0 风险面已经收敛**（之前几轮 refactor 解决了关键的"双重建"和"卡死 LL​M 流"问题）。

**但代码体积和职责集中度已经到临界点：**

- `IngestOrchestrator.kt` **2793 行**（单文件）
- `KnowledgeRepositoryImpl.kt` **1671 行**，构造函数 18 个 DAO
- `AiGateway.kt` **767 行**，4 处重复 try/catch 错误处理模板
- `AiPromptTemplates.kt` **765 行**（这个是合理的——纯模板）

测试覆盖率 **约 20%**（9 个单元测试 + 1 个迁移测试，且均集中在解析器、debouncer、JSON 解码器；**没有**对最关键的 `runUntilIdle` 4 轨并行、knowledge graph 重建、KB 迁移、cooperative cancel 的端到端测试）。

## 评审方法学

1. **业务流程追踪**：从 `NoteEditorViewModel.saveToKnowledgeBase` / `IngestQueueService` 入口出发，沿着 `ProcessingTaskScheduler` → `IngestRuntime` → `IngestOrchestrator` → 4 阶段 pipeline → `KnowledgeRepositoryImpl` → 23 个 entities 完整走一遍
2. **架构对照**：将现有实现与 `CLAUDE.md` 中描述的"4 阶段管线 + 4 轨并行 + 3 道去抖 + 3 道检查点"目标做差异分析
3. **代码质量扫描**：对单文件 ≥ 800 行的文件标记 + DRY 重复块定位 + 错误处理异常分支梳理
4. **测试盘点**：列出所有 `app/src/test/**/*.kt` 和 `androidTest/**/*.kt`，绘制"代码路径 vs 测试覆盖"矩阵
5. **性能/并发分析**：找到所有 `suspend` + `withContext` 切换、锁、原子变量、协程作用域并梳理生命周期

## 关键正面发现（先肯定好的部分）

- **P0-1 去抖（`RebuildDebouncer`）设计得很干净**：3 种预置 debounce 窗口 + `collectLatest` 自动取消 in-flight + per-KB 失败隔离，每 KB 一个独立 bucket。
- **P0-2 cooperative cancel**（`ensureActive()` per SSE line + Job-pinned）让 1MB 流式 JSON 在用户取消时能 < 50ms 退出。
- **P0-3 长源 checkpoint**（`LongSourceCheckpointStore`）用文件持久化让 ≥ 50K 字源分块分析能崩溃后恢复。
- **MIGRATION 设计扎实**：v4 → v9 全部带 `addColumnIfMissing` 检查，不强制重建。
- **`RebuildDebouncerTest`、`IngestQueuePolicyTest`、`ParseAiAnalysisJsonTest` 三个测试质量很高**，覆盖了状态机关键路径。
