# 架构评审

> 模块边界、并发模型、状态机、依赖图与 6 个架构问题

## 1. 模块边界

### 1.1 现状

```
com.my.knowledge/
├── data/
│   ├── ai/           ← AiGateway, AiPromptTemplates, AiTextCleaner, LanguageDetector, VolcengineVoice
│   ├── db/           ← AppDatabase, 23 entities, 16 DAOs
│   ├── file/         ← LocalFileStore
│   ├── ingest/       ← IngestOrchestrator (2793), IngestDao, IngestQueuePolicy, SweepReviews, ThreadEvolutionRunner, LongSourceCheckpointStore, WikiPageCompiler
│   ├── processing/   ← ProcessingTaskScheduler, RebuildDebouncer
│   ├── repository/   ← KnowledgeRepositoryImpl (1671), KnowledgSearchEngine, InspirationThreadContext
│   ├── search/       ← KnowledgeSearchResult, SemanticSearchCandidate
│   └── ...
├── domain/
│   ├── model/        ← KnowledgeEntityKind, ...
│   ├── repository/   ← KnowledgeRepository interface
│   └── usecase/      ← DeleteSourceLogUseCase, ...
├── worker/           ← IngestWorker, IngestRuntime, LlmInspirationThreadWorker, ThreadEvolutionWorker, SummaryWorker, TagWorker, ArchiveRecommendWorker
├── viewmodel/        ← NoteEditorViewModel, AskViewModel, ProfileViewModel, ...
└── ui/               ← DependencyProvider (DI 容器)
```

### 1.2 问题

**ARCH-1：领域层被数据层反向依赖**（P1）

`KnowledgeRepositoryImpl` 在 `com.my.knowledge.data.repository` 包，但它的 *Worker* 包装（`ThreadEvolutionWorker`, `LlmInspirationThreadWorker`）在 `com.my.knowledge.worker` 包里要 `import com.my.knowledge.data.repository.KnowledgeRepositoryImpl` 并显式 `new` 一个，**绕过**了 `DependencyProvider`：

```kotlin
// ThreadEvolutionWorker.kt:46-58
private fun getRepository(db: AppDatabase): KnowledgeRepository {
    return KnowledgeRepositoryImpl(   // ← 硬 new
        db.knowledgeBaseDao(), db.knowledgeItemDao(),
        // ... 18 个 DAO 硬编码
    )
}

// LlmInspirationThreadWorker.kt:313-323
private fun newRepository(db: AppDatabase): KnowledgeRepository = KnowledgeRepositoryImpl(...)
```

DI 容器存在但被绕过。**修复方向**：让 Worker 通过 `WorkerFactory` + `assistedInject` 或更轻的 `EntryPoint` 获取依赖。

**ARCH-2：数据层耦合 worker 子系统**（P1）

`IngestRuntime` 是 `object`（全局单例）但通过 `DependencyProvider.provideKnowledgeRepository` 拿依赖 → 静态访问 → 无法在测试中替换。

**ARCH-3：`IngestOrchestrator` 是事实上的"工作流引擎"**（P0）

2793 行实现的 4 阶段管线 + 4 轨并行 + cache hit 检查 + 长源 checkpoint + cooperative cancel 全部耦合在一个类里：
- 状态机：`pending → running → completed/failed` 散落在 `processing_task` 表
- 调度：手写的 `AtomicInteger` 计数器 + `withLocks` Mutex 嵌套
- 持久化：每阶段都直写 DAO

这不是单一职责，这是"在 Room 之上手写了一个简化版 Temporal/Cadence"。

**重构方向**（详见 [06-改进路线图](./06-改进路线图.md)）：
1. 抽出 `IngestPipeline` 接口（4 阶段抽象）
2. 抽出 `IngestScheduler`（4 轨并行 + 锁）
3. 抽出 `IngestStateMachine`（pending/running 转换）
4. 保留 `IngestOrchestrator` 作为 facade 协调三者

**ARCH-4：23 个 entities，19 个 DAOs——领域粒度还可以，但分散的 JSON 列说明领域未稳定**（P2）

多数关键实体（`AnalysisResultEntity`）的"业务数据"用 `*Json` 字符串列存（`tagsJson`, `entitiesJson`, `relationsJson`, `claimsJson`, `gapsJson` 等）。这是 Room 通用反模式——**失去了 Room 的查询能力**：
- 无法按 `entitiesJson` 内容过滤
- 无法 JOIN
- `tagsJson` 内容更新要走 read-modify-write

*虽然短期合理*（避免频繁迁移），但 medium-term 应当用 `TypeConverter` + 关联表拆出来，或上 `kotlinx.serialization` 持久化类。

**ARCH-5：Knowledge Graph 三层关系在同一个 entity 集合里**（P2）

`KnowledgeEntityEntity` + `KnowledgeRelationEntity` + `KnowledgeCommunityEntity` 都在 `KnowledgeGraphDao` 一次性返回，但**没有领域模型**层（只有 rowid）。`rebuildGraphForBase` 的 dedup 逻辑（`name+type`）是字符串匹配的硬编码。

**ARCH-6：缓存快路径在 `isIngestCacheHit` 但 key 不可配置**（P2）

Cache key 是 `sha256(markdown)` 1:1 对齐 llm_wiki，但**没法按 KB 或按 prompt version 区分**。如果将来 prompt 升级，cache 会持续命中 → 用旧版分析结果。

**修复方向**：cache key 包含 `promptVersion`（已经存在 `AnalysisResultEntity.promptVersion`）。

## 2. 并发模型

### 2.1 协程作用域清单

| 作用域 | 类型 | 生命周期 | 关键使用点 |
| --- | --- | --- | --- |
| `IngestRuntime.scope` | `SupervisorJob + Dispatchers.IO` | App process | 摄入管线 |
| `RebuildDebouncer.externalScope` | `SupervisorJob + Dispatchers.IO` | App process | 4 种去抖动作 |
| `WorkManager Worker` | per-CoroutineWorker | WorkManager 调度 | 后台任务 |
| `viewModelScope` | per-ViewModel | ViewModel 存活 | UI 状态 |
| `IngestOrchestrator` 内部 | ad-hoc coroutineScope | runUntilIdle 调用 | 4 轨并行 |

### 2.2 锁清单

| 锁 | 类型 | 范围 | 用途 |
| --- | --- | --- | --- |
| `IngestRuntime.runMutex` | Mutex | 全局 | 防止多 worker 并发 runOnce |
| `withLocks(kbId)` | KB 写锁 (per-kb) | 同 KB | wiki 页面合并 |
| `RebuildDebouncer.buckets` | ConcurrentHashMap + Job | per-kb+kind | 4 种去抖动作互斥 |
| `processing_task` 状态 | DB 唯一约束 | DB | 同 task 不能 2 进程同时跑 |

### 2.3 并发不变量（与实现对照）

| 不变量 | 现状 | 评价 |
| --- | --- | --- |
| 同 source 的 parse→analysis→generation 串行 | `shouldClaimNextSameSourceTask` 控制 | ✅ 实现正确 |
| 同 KB 写操作串行 | `withLocks(kbId)` | ✅ 实现正确 |
| 跨 KB 完全并行 | 4 轨独立抢任务 | ✅ 实现正确 |
| cooperative cancel 让流式 LLM 立即退出 | `ensureActive()` per SSE line | ✅ 实现正确 |
| 进程崩溃后能从检查点恢复 | `LongSourceCheckpointStore` + 启动 `recoverSourcesWithoutActiveTasks` | ✅ 实现正确 |
| rebuild 不阻塞 ingest | 拆到 RebuildDebouncer off-lock | ✅ P0-1 已修 |
| 4 轨并行没有死锁/饥饿保护 | 依赖 `withLocks` 公平性 + `AtomicInteger` 计数 | ⚠ 没有测试守护 |

**CONC-1：并发模型的"测试守护"缺失**（P1）

`runUntilIdle` 的 4 轨模型没有任何 unit test。一旦有人误把 `withContext(IO)` 改为 `withContext(Default)`，或把 `AtomicInteger` 换成普通 Int，所有并发不变量都会破，但没有 CI 失败信号。

**修复方向**：见 [04-测试覆盖评审.md](./04-测试覆盖评审.md)

## 3. 状态机

### 3.1 ProcessingTask 状态

```
              enqueue
   (none) ────────────────▶ pending
                              │
                              │ 抢到
                              ▼
                            running
                          /   │   \
                  success /    │    \ fail
                        /      │      \
                       ▼       ▼       ▼
                  completed  failed  pending (retry)
                                          │
                                          │ retry 触发
                                          └──────▶ running
```

**实现位置**：散落在 `ProcessingTaskDao`（transition SQL）+ `IngestOrchestrator`（业务触发）。
**问题**：状态转换没有集中校验（例如：不允许 `completed → running`）。如果未来加一个 worker 错误地 UPDATE 状态，会破坏不变量。

**SM-1：缺少显式状态机**（P2）
**修复方向**：抽 `ProcessingTaskStatus` 枚举 + `transitionTo(newStatus): Result<Unit>` 函数，统一校验。

### 3.2 KnowledgeBase 生命周期

```
createBase
    │
    ▼
   empty
    │
    │ 首次 ingest 完成
    ▼
  hasItems
    │
    │ rebuildGraphForBase
    ▼
  hasGraph
    │
    │ thread evolution
    ▼
 hasThread
```

**`threadStatus` 字段**（`"idle" / "ready" / "stale" / "failed"`）：在 `LlmInspirationThreadWorker` 设置 `"ready"`，但其他状态由谁设置？没找到 setter 路径。

**SM-2：`threadStatus` 状态机不完整**（P2）
- 只有 `"ready"` 出口
- 失败时不写 `"failed"`
- 重建中无 `"stale"` 过渡

## 5. 错误处理架构

```
Layer 1 (LLM 边界):  AiGateway.classifyHttpError
  → 友好中文错误 [鉴权失败]/[DNS 失败]/[连接失败]/[超时]/[SSL 错误]

Layer 2 (Pipeline):   IngestOrchestrator 捕获 + 写 ProcessingTaskLogEntity
  → status=failed + errorMessage
  → 调用方 UI 可见

Layer 3 (Worker):     CoroutineWorker.doWork()
  → throw → WorkManager retry (default 10s backoff)

Layer 4 (Debouncer):  RebuildDebouncer 静默 swallow
  → Log.e  → 下一轮触发时再试
  → ⚠ P1-3: 用户无感知失败

Layer 5 (Repository): KnowledgeRepositoryImpl.moveItemToBase
  → try/catch → Log.e → throw e
  → ⚠ P1-5: try/catch 仅用于日志，没有 swallow
```

**ERR-1：错误处理无统一抽象**（P1）
- 5 个层各管各的，没有 `Result<T, AppError>` 类型
- AI 错误用中文，DB 错误用 raw exception
- 用户在 UI 看到的"失败原因"不一致

**修复方向**（详见 [06-改进路线图](./06-改进路线图.md)）：
```kotlin
sealed class AppError {
    data class Ai(val kind: AiErrorKind, val raw: String?) : AppError()
    data class Database(val op: String, val cause: Throwable) : AppError()
    data class Cancelled(val by: String) : AppError()
    data class Unknown(val message: String) : AppError()
}
```

## 6. 总结：6 个架构问题

| ID | 问题 | 严重度 | 影响面 |
| --- | --- | --- | --- |
| ARCH-1 | 领域层被数据层反向依赖，Worker 绕过 DI 容器 hard-new Repository | P1 | 测试性、可替换性 |
| ARCH-2 | `IngestRuntime` 是 `object` 全局单例，无法在测试中替换 | P1 | 测试性 |
| ARCH-3 | `IngestOrchestrator` 2793 行是事实上的"工作流引擎"，单类耦合 4 职责 | P0 | 修改风险、协作阻塞 |
| ARCH-4 | 23 个 entities 的 `*Json` 字符串列，失去 Room 查询能力 | P2 | 长期演进 |
| ARCH-5 | Knowledge Graph 三层关系硬字符串 dedup，无领域模型层 | P2 | 长期演进 |
| ARCH-6 | Cache key 不含 `promptVersion`，prompt 升级会持续命中旧分析 | P2 | 正确性（间接） |
