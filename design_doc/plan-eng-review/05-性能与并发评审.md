# 性能与并发评审

> N+1、内存、并发、I/O 瓶颈与 6 个性能问题

## 1. 性能观察基线

工程在 Room + LLM 的双重 I/O 场景下，性能瓶颈由 **LLM 网络延迟** 主导（单次 LLM 调用 5-30 秒），所以"快"指的是：
- 摄入管线的"本地"段（parse、embedding、merge）< 1 秒
- 4 轨并行不浪费 token
- 搜索 < 100 ms（在 1K 实体内）
- 知识图重建可异步、不卡 UI

下面按子系统分类找出"可避免的慢"。

## 2. 摄入管线性能

### PERF-1：4 轨并行 + `maxTasks=8` 的饱和问题（P2）

**位置**：`IngestOrchestrator.runUntilIdle` 入口参数

**现状**：
- `maxTasks = 8`（一批最多 8 个 task）
- `parallelism = 4`（4 轨并发）
- 意味着 8 个 task 在 4 轨间分两批跑

**问题**：
- 8 个 task 中如果有 4 个是 LLM 调用（占满 4 轨），剩下 4 个本地任务（parse / embedding）要等
- LLM 任务完成之前，本地任务不开始
- 浪费 4 轨 × LLM 时长

**修复方向**：
- 方案 A：把 LLM task 限流到 2 轨，让出 2 轨给本地 task
- 方案 B：把"批内 task"按类型预分类，本地 task 优先
- 方案 C：单纯提高 `parallelism = 6`

**影响估算**：当前 8 task 批跑完约 30-60 秒（4 个 LLM × 20s）；优化后可压到 15-30 秒（本地 + LLM 重叠）。

### PERF-2：`parseTask` 解析后立即 `enqueue("analysis")` 触发下一轮调度（P1）

**位置**：`IngestOrchestrator.parseTask`

**现状**：
```kotlin
fun parseTask(...) {
    val parser = pickParser(source)
    val parsed = parser.parse(source)
    parsedContentDao.upsert(parsed)
    fragmentDao.upsertAll(fragments)
    enqueue(task.copy(type = "analysis", output = ...))  // ← 立即入队
}
```

**问题**：
- `enqueue` 写入 DB（1 次 IO）
- `runUntilIdle` 下一轮 `SELECT ... WHERE status='pending'` 拉出来（1 次 IO）
- 4 轨并行环境下，这种"task 接力"在 8 个文件同批导入时会产生 4-8 倍的"调度噪声"

**修复方向**：
- 同源任务**直接传引用**给下一轨，不写 DB
- 或者在 `runTask()` 里直接 `when (currentType) { ... nextStep() }` 而不写回 DB

**影响估算**：单文件 1-2 次 IO → 0 次 IO；8 文件批量约节省 16 次 IO × 0.5ms = 8 ms（不显著，但消除了 race 窗口）。

### PERF-3：`generationTask` 流式响应缓存到内存再写 DB（P2）

**位置**：`IngestOrchestrator.generationTask`（估计）

**现状**：
```kotlin
val fullBuffer = StringBuilder()
aiGateway.streamJson(...).collect { chunk ->
    fullBuffer.append(chunk)        // ← 内存累积
    throttledProgress(chunk)
}
val parsed = parseAiGenerationJson(fullBuffer.toString())  // ← 解析完整 buffer
```

**问题**：
- 大 markdown 生成可能产生 5-10 MB 文本，全在 heap
- OOM 风险（虽然单源 10MB 不会 OOM，但若 LLM 失控会）

**修复方向**：
- 解析为流式 JSON parser（`json-kotlinx` / `moshi` 都支持）
- 或硬上限：`if (fullBuffer.length > 50_000_000) error("AI 输出超限")`

**影响估算**：当前安全；防御性改进。

### PERF-4：长源 checkpoint 文件持久化频率（P2）

**位置**：`LongSourceCheckpointStore`（推断）

**问题**（推断，无源码确认）：
- 如果每个 chunk 完成都写一次 checkpoint（f-sync），磁盘 I/O 翻倍
- 应使用 buffered / debounced 写

**修复方向**：仅在 chunk 边界写，且不需要 `fsync`。

## 3. 知识图谱重建性能

### PERF-5：`rebuildGraphForBase` 全量重建无增量（P1）

**位置**：`KnowledgeRepositoryImpl.rebuildGraphForBase`（第 521 行附近）

**现状**：
- 每次触发都全表读取 knowledge_item + knowledge_fragment
- 全表删除 knowledge_entity/relation/community
- 全表插入新值
- 单 KB 含 1000 items 时约 5-15 秒

**问题**：
- 每次 ingest 触发 → 重建整个 KB 图
- 一个 KB 内 10 items 时 rebuild ≈ 0.5s，可接受
- 一个 KB 内 100+ items 时 rebuild ≈ 5s+ → **用户感受到延迟**
- 配合 `RebuildDebouncer` 1s debounce，仍然可能阻塞 1 个 generation 的后半段

**修复方向**：
- 增量重建：diff 模式（新增/删除/修改的 items）
- 或者：把"重建"拆为"更新图谱"（recompute centrality + 增量 entities/relations）
- 短期：`RebuildDebouncer` 已经把 rebuild 拆出锁外，所以不阻塞 ingest——但仍占 IO

**影响估算**：100 item KB 从 5s 压到 1s（增量）。

### PERF-6：`rebuildFragmentsForItem` 16 维 hash-bucket embedding（P2）

**位置**：`KnowledgeRepositoryImpl.rebuildFragmentsForItem`（第 463 行附近）

**现状**：
- 用 hash 函数生成 16 维"假"向量
- 每个 fragment 存一行到 `knowledge_embedding`
- 语义搜索时取所有 candidates 在内存里算 cosine 相似度

**问题**：
- 16 维 hash-bucket 几乎不携带语义信息
- "语义搜索"实际退化为"updatedAt DESC 排序"
- 用户感受：搜索结果与关键词不匹配

**修复方向**：
- 短期：在 UI 标注"语义搜索为占位实现"
- 长期：上 Sentence-Bert / 端侧小模型（如 `all-MiniLM-L6-v2` 量化版）算真向量

**影响估算**：搜索准确率从 ~30% 提到 ~85%（参考 Sentence-Bert 公开 benchmark）。

## 4. 搜索性能

### PERF-7：`SearchDao` 8 个查询用 `LIKE '%query%'` 前缀通配（P0）

**位置**：`SearchDao.kt` 全文

**现状**：
```sql
SELECT * FROM knowledge_item
WHERE (title LIKE '%' || :query || '%' OR contentMarkdown LIKE '%' || :query || '%')
  AND deletedAt IS NULL
```

**问题**：
- SQLite 无法使用任何索引（LIKE 前导通配 = 全表扫描）
- 单 KB 1K items → 100ms 级别
- 单 KB 10K items → 1-5 秒（用户可感知的卡顿）

**修复方向**：
- 已有 `KnowledgeItemFts`（FTS4）！但只有两个方法用 FTS（`ftsSearchAll`, `ftsSearchByKb`）
- 把所有 `searchXxx` 路由到 `ftsSearchXxx`
- 关键字搜索 vs 全文搜索分开：短词（≤ 3 字）走 LIKE，长词走 FTS

**影响估算**：1K items 从 100ms → 5ms（20x 提升）；10K items 从 5s → 50ms（100x 提升）。

### PERF-8：所有搜索返回 `Flow<List<...>>`（P1）

**位置**：`SearchDao.kt`

**问题**：
- 搜索是命令式操作，用户输入 → 一次查询
- Flow 包装徒增开销：Flow 订阅/发射/取消的开销 ~1-5ms
- 多次相同查询应缓存，但 Flow 不自然支持

**修复方向**：
- `searchXxx` 改为 `suspend fun` 或普通 `fun` 返回 `List`
- `ftsSearchXxx` 保持 `Flow`（增量监听场景）——但当前没有"增量监听搜索结果"的实际使用
- 或者用 `conflate()` 包装 Flow

**影响估算**：搜索响应延迟降低 1-5ms。

## 5. 内存与缓存

### PERF-9：`IngestRuntime` 全局缓存 SHA-256 digest（P2）

**位置**：`IngestRuntime` / `IngestOrchestrator`（推断）

**问题**：
- `MessageDigest.getInstance("SHA-256")` 不便宜（每次拿要查安全 provider）
- 现状：可能每次都新建（推断）

**修复方向**：
- 抽 `Sha256Hasher` 单例，缓存 `MessageDigest` 实例
- 大文件分块 hash 时尤其重要

### PERF-10：UI 端 FTS4 索引未启用 `tokenize='unicode61 remove_diacritics 1'`（P2）

**位置**：`KnowledgeItemFts`（推断实体定义）

**问题**：
- FTS4 默认 tokenize 是 `simple`（按空格 + 标点）
- 中文搜索分词效果差
- 现状中文查询经常搜不到

**修复方向**：
- 改用 `tokenize = "unicode61 remove_diacritics 1"` 或集成 jieba 等中文分词器
- 短期：加 LIKE 兜底（已有 `searchAll`）

## 6. 协程与线程

### PERF-11：4 轨 `withContext(IO)` 但没有限流（P1）

**位置**：`IngestOrchestrator` 内部 4 轨

**现状**：
- 4 个 Lane 各自 `launch(Dispatchers.IO) { ... }`
- 每个 Lane 内可能有多个 IO 调用 + LLM 网络调用
- LLM 调用阻塞 Lane，**不释放线程池**

**问题**：
- `Dispatchers.IO` 默认 64 线程（`kotlinx.coroutines.scheduler`）
- 4 轨都用 IO 调度器，IO 池子空闲
- 但 LLM 调用阻塞线程 → IO 池的 `max(64)` 不够会卡？
- 不会卡，但 4 轨 4 个 LLM 同时打 LLM 服务端 → 触发服务端限流

**修复方向**：
- LLM 调用走专门的 `Dispatchers.IO.limitedParallelism(2)` 限流到 2 个并发
- 本地 task 走默认 IO

**影响估算**：服务端 429 减少 50%。

## 7. 数据库性能

### PERF-12：单条 insert vs 批量 insert（P1）

**位置**：多处 DAO（具体待盘）

**问题**：
- `rebuildGraphForBase` 一次写 N 个 entity / N 个 relation
- 若每行单独 INSERT → N 次 IO
- 应用 `@Insert` + `OnConflictStrategy.REPLACE` + 批量方法

**修复方向**：
- 检查所有 `*Dao.kt` 的 `@Insert` / `@Update` 签名
- 优先用 `@Upsert` + 列表参数

### PERF-13：频繁事务开销（P2）

**位置**：`KnowledgeRepositoryImpl` 多处 `@Transaction`

**问题**：
- 每个事务 ~1-2ms
- `rebuildGraphForBase` 内含 5+ 事务（entity/relation/community/delete-then-insert）
- 可合并为 1 个大事务

**修复方向**：审查 `@Transaction` 边界，合并连续同源操作。

## 8. 总结：6 个性能问题

| ID | 问题 | 严重度 | 影响面 |
| --- | --- | --- | --- |
| PERF-1 | 4 轨并行 + maxTasks=8 LLM 占满，本地任务等待 | P2 | 8 文件批导入慢 2x |
| PERF-2 | parse → analysis 通过 DB 接力，多余 IO | P1 | 8 文件批 16 次多余 IO |
| PERF-3 | generationTask 流式全 buffer 在内存 | P2 | OOM 风险（防御性）|
| PERF-5 | rebuildGraphForBase 全量重建 | P1 | 100+ item KB 慢 |
| PERF-7 | `SearchDao` 8 处 `LIKE '%q%'` 前缀通配 | P0 | 10K items 卡 5s |
| PERF-8 | `SearchDao` Flow 包装命令式操作 | P1 | 多余 1-5ms 延迟 |
| PERF-11 | LLM 调用未限流 | P1 | 服务端 429 |
| PERF-12 | 部分 DAO 单条 insert | P1 | N+1 隐患 |

## 9. 性能优化路线（按 ROI 排序）

1. **PERF-7** 路由搜索到 FTS（1 天工，10x-100x 提升）→ **P0**
2. **PERF-5** 增量重建图谱（3 天工，5x 提升）→ **P1**
3. **PERF-11** LLM 限流 2 并发（0.5 天工，429 减半）→ **P1**
4. **PERF-8** 搜索去 Flow（0.5 天工，1-5ms 提升）→ **P1**
5. **PERF-2** 同源任务去 DB 接力（1 天工，去 race 风险）→ **P1**
6. **PERF-12** DAO 批量 insert（1 天工，可观提升）→ **P1**
7. **PERF-1** 4 轨饱和调度优化（1 天工，2x 提升）→ **P2**
8. **PERF-3** 流式 JSON parser（1 天工，OOM 防御）→ **P2**
9. **PERF-6** 真语义向量（5+ 天工，搜索准确率飞跃）→ **P2**
10. **PERF-9** SHA-256 单例（0.5 天工，可忽略）→ **P3**
